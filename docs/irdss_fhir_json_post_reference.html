Intelligent Referral Decision Support System

FHIR, JSON, and the POST Method

A plain-language reference to the healthcare data format used between the Mock Hospital and the IRDSS Interoperability Layer (IOL).

Purpose of this paper

This paper explains what FHIR and JSON mean, which FHIR-style fields are defined by the current IOL server, what data the Mock Hospital sends, and how the HTTP POST method delivers a new referral.

IRDSS Prototype Reference Paper 1

Background

Understanding FHIR and JSON

What is FHIR?

FHIR means Fast Healthcare Interoperability Resources. It is a healthcare information standard developed by HL7. It provides agreed names and structures for information that different health systems need to exchange.

Instead of every hospital inventing a different label and layout for the same information, FHIR organizes information into reusable “resources.” Examples include a Patient for demographics and an Encounter for an interaction involving a patient.

What is JSON?

JSON means JavaScript Object Notation. It is a simple text format that computers can create, send, read, and validate. JSON stores information as labeled values. Curly braces contain one object, square brackets contain a list, and a colon separates a label from its value.

FHIR

Defines what the healthcare information means and how it is organized.

JSON

Writes that information in a format that computer systems can exchange.

POST

Delivers the completed JSON to an API to create a new referral.

A small example

{
  "resourceType": "Patient",
  "id": "P-000026",
  "gender": "female",
  "birthDate": "1997-05-15"
}
PartPlain-language meaning
resourceTypeThis tells the receiving system that the object represents a FHIR Patient.
idThis is the hospital’s identifier for the patient record.
genderThis contains the recorded gender value.
birthDateThis contains the date of birth using year-month-day format.
Simple comparison: FHIR is like an agreed healthcare form, JSON is the typed version of that form, and POST is the courier that delivers it to the IOL.

IOL definition

FHIR-style structure accepted by the IOL

The IOL server uses Python validation models to check an incoming referral. The main model is named ReferralRequestSchema. It currently requires the following top-level fields.

IOL fieldRequired?Purpose in the current system
resourceTypeYesIdentifies the referral payload as an Encounter.
statusYesShows the state of the encounter; the Mock Hospital sends planned.
subjectYesReferences the patient using Patient/{id} and may include a display name.
reasonCodeYesA list containing one primary referral reason and up to three additional reasons.
patient_recordYesContains the Patient object needed by the current IOL workflow.

Nested definitions used by the IOL

DefinitionFieldsMeaning
FHIRSubjectreference, optional displayConnects the referral to the patient.
FHIRReasonCodetext, optional codingDescribes why the patient is being referred.
FHIRCodingsystem, code, displayProvides a computer-readable code and a human-readable label.
FHIRPatientresourceType, id, name, gender, birthDate, extensionContains the patient demographics and IRDSS-specific information.
FHIRNamefamily, list of given namesSeparates surname from given names.
FHIRExtensionurl plus decimal, string, or Boolean valueAdds information needed by IRDSS that is not placed in the basic Patient fields.

Validation applied by the IOL

  • The referral must contain between one and four referral reasons.
  • Each reason must contain text and must not exceed 255 characters.
  • Duplicate referral reasons are rejected.
  • The Patient must contain an ID, at least one name entry, a birth date, and an extension list.
Important: patient_record is an IRDSS-specific wrapper. It helps the present prototype send an Encounter and Patient together, but it is not a standard field of the official FHIR Encounter resource.

Source in the current IOL: app/schemas/encounter.py, app/schemas/patient_schema.py, and app/schemas/fhir_base_schema.py.

Payload reference

Meaning of the data sent by the Mock Hospital

Payload sectionInformation representedHow IRDSS uses it
EncounterThe planned patient referral event.Starts the referral workflow.
subjectThe patient reference and display name.Links the referral to the correct patient.
reasonCodePrimary reason followed by optional additional reasons.Explains the referral and supports analytics.
patient_recordPatient demographics and extensions.Supplies the clinical and demographic data required for matching and care coordination.
serviceProviderThe referring hospital as an Organization reference.Sent by the Mock Hospital, but not currently declared in the IOL request validation schema.

Extensions currently produced by the Mock Hospital

GroupExamples
Referral and clinical informationSeverity, chief complaint, diagnosis, salary used by the prototype ranking logic, latitude, and longitude.
Contact and demographicsPhone, address, civil status, PhilHealth number, and PhilHealth membership status.
Vital signsBlood pressure, heart rate, respiratory rate, temperature, oxygen saturation, height, and weight.
Patient indicatorsPWD, pregnant, senior citizen, has allergy, and allergy details.
Consent informationConsent status, method, text version, recorded time, witness, signer type, signer name, representative relationship, and document SHA-256 hash.

Why extensions are used

FHIR extensions provide a structured way to add information needed by a particular project. Each extension includes a URL that identifies its meaning and a value such as text, a number, or true/false.

{
  "url": "http://irdss.gov.ph/fhir/StructureDefinition/isPregnant",
  "valueBoolean": true
}

For use outside the current prototype, the IRDSS extension URLs and their rules should be formally published so another FHIR system can interpret them correctly.

CURRENT

The IOL accepts one combined, FHIR-style referral payload designed for the IRDSS workflow.

FUTURE

Full FHIR exchange should use standalone Patient, Encounter, Condition, Observation, ServiceRequest, Consent, and DocumentReference resources.

Data transmission

How POST sends the referral to the IOL

POST is an HTTP method used when a client asks a server to create or process a new record. In IRDSS, the Mock Hospital uses POST when initiating a referral.

Mock Hospital UIUser submits the referral form
→
PHP BackendCreates and signs the JSON
→
IOL ServerValidates and creates the referral

POST request

POST /api/v1/referral/initiate HTTP/1.1
Host: <iol-server>:8081
Content-Type: application/json
X-System-Code: SYSTEM-001
X-Key-ID: KEY-2026-001
X-Signature-Timestamp: <current-time>
X-Request-Nonce: <unique-random-value>
X-System-Signature: <rsa-signature>

{ "resourceType": "Encounter", "status": "planned", ... }

Processing sequence

  1. The browser submits ordinary form data to the Mock Hospital PHP backend.
  2. The backend reads the selected patient from the local MySQL database.
  3. It creates the FHIR-style Encounter and Patient JSON shown in this paper.
  4. It calculates a SHA-256 hash of the exact body and signs the request with the hospital’s RSA private key.
  5. The IOL verifies the sender, timestamp, unique nonce, signature, and request schema.
  6. The IOL stores the referral and returns referral identifiers as JSON.

Example successful response

{
  "status": "success",
  "message": "Referral initiated successfully",
  "referral_tracking_id": "TRK-2026-000123",
  "referral_id": "ref_35b0cfd39e9f"
}
Security clarification: The RSA signature verifies the sender and detects changes to the JSON. It does not hide the patient data. A production deployment must also use HTTPS/TLS.
