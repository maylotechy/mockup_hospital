How the Mock Hospital packages referral information and sends it to the IRDSS Interoperability Layer (IOL).

Part 1

FHIR represented as JSON

FORMATJSON

A text format composed of named properties, values, objects, and arrays.

STANDARDFHIR

Defines reusable healthcare resources such as Patient and Encounter.

TRANSPORTHTTP POST

Sends a new referral representation to a server endpoint.

Basic FHIR Patient in JSON

{
  "resourceType": "Patient",
  "id": "P-000026",
  "name": [{
    "family": "Patient",
    "given": ["Sample"]
  }],
  "gender": "female",
  "birthDate": "1997-05-15"
}

How to read it

ElementExplanation
resourceTypeIdentifies which FHIR resource is represented.
idLogical identifier used to reference this patient.
nameAn array because a patient can have more than one recorded name.
genderA coded demographic value.
birthDateA FHIR date written as YYYY-MM-DD.
Presentation line: “FHIR does not replace JSON. FHIR tells us what healthcare fields mean, while JSON is one way of writing those fields for computer exchange.”

FHIR also supports XML and RDF, but the IRDSS prototype uses JSON.

Part 2

JSON currently sent by the Mock Hospital

The PHP backend builds an Encounter payload and embeds a Patient record required by the current IOL request schema.

{
  "resourceType": "Encounter",
  "status": "planned",
  "subject": {
    "reference": "Patient/P-000026",
    "display": "Sample Patient"
  },
  "reasonCode": [{
    "coding": [{
      "system": "http://irdss.gov.ph/fhir/CodeSystem/referral-reason",
      "code": "NO_AVAILABLE_ICU",
      "display": "No Available Intensive Care Unit"
    }],
    "text": "No Available Intensive Care Unit"
  }],
  "patient_record": {
    "resourceType": "Patient",
    "id": "P-000026",
    "name": [{ "family": "Patient", "given": ["Sample"] }],
    "gender": "female",
    "birthDate": "1997-05-15",
    "extension": [
      {
        "url": "http://irdss.gov.ph/fhir/StructureDefinition/diagnosis",
        "valueString": "Pneumonia"
      },
      {
        "url": "http://irdss.gov.ph/fhir/StructureDefinition/vitalHeartRate",
        "valueDecimal": 90
      }
    ]
  },
  "serviceProvider": {
    "reference": "Organization/FAC-000015",
    "display": "Sample Provincial Hospital"
  }
}

Accuracy note: This is a FHIR-style IRDSS payload, not yet a fully standard FHIR transaction. patient_record is an IOL-specific wrapper. Diagnosis and vitals currently use custom extensions.

Sending the JSON using POST

Mock Hospital UIReferral form
→
PHP BackendBuilds and signs JSON
→
IOL APIValidates and creates referral

HTTP request

POST /api/v1/referral/initiate HTTP/1.1
Host: <iol-server>:8081
Content-Type: application/json
X-System-Code: SYSTEM-001
X-Key-ID: KEY-2026-001
X-Signature-Timestamp: <unix-time>
X-Request-Nonce: <unique-random-value>
X-System-Signature: <rsa-signature>

{ "resourceType": "Encounter", "status": "planned", ... }

What happens during the POST request?

  1. The user submits the referral form to the Mock Hospital PHP backend.
  2. PHP reads the selected patient from the hospital’s local MySQL database.
  3. PHP converts the necessary data into the FHIR-style Encounter and Patient JSON.
  4. The backend calculates a SHA-256 body hash and signs the request using the hospital’s RSA private key.
  5. The IOL verifies the public key signature, timestamp, nonce, facility, and JSON schema.
  6. If valid, the IOL creates the referral and returns a JSON response.

Example IOL response

{
  "status": "success",
  "message": "Referral initiated successfully",
  "referral_tracking_id": "TRK-2026-000123",
  "referral_id": "ref_35b0cfd39e9f"
}

Part 4

What to emphasize in the report

Implemented now

  • FHIR-style Encounter and Patient JSON
  • Patient and Organization references
  • Coded primary and additional referral reasons
  • Custom extensions for diagnosis, vitals, flags, and consent
  • POST endpoint for initiating referrals
  • Schema validation on the FastAPI IOL server
  • RSA-signed requests with timestamp and nonce

Next interoperability step

  • Send demographics as a standalone Patient
  • Send diagnoses as Condition
  • Send each vital sign as Observation
  • Represent the referral with ServiceRequest
  • Package related resources in a transaction Bundle
  • Publish and validate IRDSS profiles and extensions
  • Use HTTPS/TLS in production
Important: RSA signing proves the sender and detects changes to the body. It does not encrypt patient data; HTTPS is still required for production confidentiality.

Short reporting script

“In IRDSS, FHIR gives our referral data healthcare meaning, JSON makes that information machine-readable, and the HTTP POST method sends a new referral to the IOL. The mock hospital’s PHP backend constructs an Encounter containing a Patient record, referral reasons, hospital reference, and IRDSS extensions. It signs the exact JSON body using the hospital’s private key, then posts it to /api/v1/referral/initiate. The IOL verifies the request, validates the schema, creates the referral, and responds with its referral and tracking identifiers. Our current payload is FHIR-style and designed for this prototype; full external FHIR interoperability will require separate standard resources and a transaction Bundle.”
